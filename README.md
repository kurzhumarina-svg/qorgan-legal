# QORGAN Legal

Сайт юридической компании + AI-помощник в Telegram + админка заявок.
Домашнее задание №5.

Три части — один проект, одна база и одна общая таблица заявок.

---

## Быстрый старт

```bash
npm install
cp .env.example .env.local     # заполнить значения, см. ниже
npm run db:push                # создать таблицы в Neon
npm run dev                    # http://localhost:3000
```

Админка: `http://localhost:3000/admin`, пароль — из `ADMIN_PASSWORD` в `.env.local`.

## Что нужно получить

| Что | Где взять | Куда вписать |
|:--|:--|:--|
| База Postgres | [neon.com](https://neon.com) → проект → Connection string (**Pooled**) | `DATABASE_URL` |
| Ключ модели | Groq / OpenRouter / Mistral — см. `.env.example` | `AI_API_KEY`, `AI_BASE_URL`, `AI_MODEL` |
| Токен бота | [@BotFather](https://t.me/BotFather) → `/newbot` | `TELEGRAM_BOT_TOKEN` |
| Свой chat_id | написать своему боту, затем `npm run tg:chat -- --save` | `TELEGRAM_ADMIN_CHAT_ID` |

Пароль админки, соль сессии и секрет вебхука уже сгенерированы в `.env.local`.

> **Важно:** откройте своего бота и нажмите **Start**. Telegram запрещает боту писать
> первым тому, кто с ним не начинал диалог, — без этого уведомления администратору
> не придут, хотя код будет полностью рабочим.

# Как это устроено

Раздел для защиты: почему сделано именно так.

## Главное решение: одна таблица на два источника

Заявка с сайта и обращение из Telegram — это **одна и та же запись** в таблице `leads`,
отличается только поле `source`. Обе дороги сходятся в единственной функции
[`createLead()`](src/lib/leads.ts), которая пишет в базу, нормализует телефон и шлёт
уведомление администратору.

```
форма на сайте  ─┐
                 ├─→ createLead() ─→ таблица leads ─→ админка (общий список)
Telegram-бот ────┘         └─→ notifyAdmin() ─→ уведомление в Telegram
```

Поэтому «работают как один продукт» — не результат ручной синхронизации, а следствие
структуры кода: заводить заявку другим способом попросту негде.

## Одна схема валидации на три места

[`leadInputSchema`](src/lib/validation.ts) используется:

1. в форме на сайте — до отправки;
2. в `POST /api/leads` — на сервере, потому что данным из браузера доверять нельзя;
3. при разборе аргументов функции `create_lead`, которую вызывает бот.

Бот физически не может создать заявку, которую форма отвергла бы: правило описано один раз.

## Бот: почему это именно AI-диалог

Клиент пишет свободным текстом, модель сама определяет направление и решает, что уточнить.
Меню из кнопок здесь не подошло бы — ТЗ требует понимания произвольных формулировок
вроде «дал знакомому деньги, теперь не возвращает».

**Function calling.** Модель не пишет заявку текстом, который потом пришлось бы разбирать
регулярками. Она вызывает функцию [`create_lead`](src/lib/ai/tools.ts) со строго
описанными полями — их остаётся проверить и записать.

**Память диалога.** История лежит в `tg_conversations`, по одной строке на чат. На Vercel
функция живёт только во время запроса и ничего не помнит между сообщениями, поэтому
состояние обязано храниться в базе.

**Дедупликация.** Telegram повторяет доставку, если не получил ответ вовремя. Таблица
`tg_updates` с `update_id` в первичном ключе гарантирует, что одно сообщение обработается
один раз — иначе клиент получал бы дубли ответов, а в базе появлялись бы две заявки.

## Защита от выдуманных законов и обещаний — два слоя

ТЗ обещает отдельно проверить три вещи: вопрос про долг, просьбу назвать статью закона
и «я точно выиграю?». Одного промпта для этого мало: промпт — это просьба, а не гарантия.

**Слой 1 — [системный промпт](src/lib/ai/prompt.ts).** Запреты сформулированы явно,
с объяснением причины и примерами правильных ответов на все три провокации.

**Слой 2 — [программная проверка](src/lib/ai/guardrails.ts).** Каждый ответ модели перед
отправкой клиенту проверяется регулярными выражениями на три вещи:

| Проверка | Что ловим |
|:--|:--|
| Ссылка на норму | `ст. 123`, `статья 456`, `ГК РК`, `ГПК РК` |
| Обещание исхода | «гарантирую», «100 %», «точно выиграете» |
| Лишние данные | просьба прислать ИИН, паспорт, реквизиты карты |

Сработало — одна повторная попытка с корректирующей инструкцией. Не помогло — уходит
безопасный шаблонный ответ. Клиент в любом случае не увидит выдуманную статью закона.

Проверка запускается автоматически: `npm run test:bot` прогоняет пять сценариев,
включая все три из ТЗ, и печатает ✓/✗ по каждому.

## Форма понимает, что заинтересовало

Клик по карточке услуги или по примеру ситуации на первом экране не просто прокручивает
страницу — он подставляет тему и текст в форму через
[общий контекст](src/components/site/lead-form-context.tsx). Человеку остаётся ввести
имя и телефон.

## Устойчивость к сбоям провайдера

Бесплатные модели живут в общем пуле и регулярно отвечают 429 «занято». Поэтому
в [клиенте модели](src/lib/ai/client.ts) есть повторы с нарастающей паузой
(1,5 → 5 → 12 секунд, а если провайдер прислал заголовок `Retry-After` — столько,
сколько он просит) и цепочка запасных моделей из `AI_MODEL_FALLBACK`. Если основная
перегружена, ответ придёт от следующей, а не оборвётся ошибкой.

Уведомление администратору отправляется в `try/catch` уже **после** записи заявки:
недоступность Telegram не должна стоить компании обращения клиента.

## Провайдер модели не зашит в код

Общение с моделью идёт через OpenAI-совместимый интерфейс, который поддерживают Groq,
OpenRouter, Mistral, DeepSeek, Gemini и локальная Ollama. Провайдер выбирается тремя
переменными в `.env.local`. Это оказалось не теоретическим удобством: Gemini был
недоступен из нужной сети, и переключение заняло минуту вместо переписывания кода.

## Дизайн

«Қорған» — крепость, защита. Отсюда цвет тянь-шаньской ели вместо привычного
юридического тёмно-синего и сине-зелёный акцент вместо золота. Никаких весов,
молотков и обещаний «выиграем 100 %»: ТЗ это прямо запрещает, и честность здесь —
часть позиционирования.

Главный элемент первого экрана — само поле «опишите ситуацию», потому что
единственная задача страницы состоит ровно в этом.

Шрифты подобраны с кириллицей как основным алфавитом: **Golos Text** (интерфейсный,
знакомый по государственным сервисам) и **Unbounded** в заголовках.

## Границы решения

Честно о том, что сделано на учебном уровне:

- **Авторизация админки** — один пароль и подписанная кука. Для продакшена нужны
  учётные записи, роли и журнал действий.
- **Бесплатные тарифы моделей** ограничены по числу запросов в минуту и могут
  использовать переписку для обучения. Для реальной юридической практики нужен
  платный тариф с договором о защите данных.
- **Персональные данные.** Бот намеренно не собирает ИИН, паспорт и реквизиты —
  и по требованию ТЗ, и потому что хранить их в учебном проекте нельзя.
- **Данные компании и сотрудников вымышленные.**

Next.js 16 (App Router), TypeScript, Tailwind CSS 4, Drizzle ORM, Neon Postgres,
OpenAI SDK как универсальный клиент к модели, Telegram Bot API напрямую через fetch.
